# Sift 架构说明

> 两个前端（Tauri + Svelte、GPUI Kit 原生）共享同一份 Rust 核心。
> 本文说明分层、关键设计决策、以及 2TB/<60s 的实测依据。

## 1. 目标与约束

| 需求 | 落地方式 |
|---|---|
| 保留原有 Tauri 方案，同时新增 GPUI 原生方案 | 两个前端 crate 都只做「适配」：命令注册、事件翻译、渲染。产品逻辑全部在共享 crate 里 |
| 架构分离，符合 Rust 工程习惯 | 按**能力**分 crate，依赖单向向下，不允许反向依赖或跨前端复用内部实现 |
| 2TB 磁盘 < 60s 扫完 | 平台批量枚举（macOS `getattrlistbulk`）+ 目录节点 arena + 名称 interner + 焦点确定性优先 + 并行 I/O 与单线程建树 |
| 内存尽量低 | 目录节点 72 字节定长记录、文件不建节点、名称去重、硬链接表只收多链接文件、扫描结束 `shrink_to_fit`、节点/深度预算 + 超预算子树「只计大小」 |
| 扫描后由 AI 判定可删性/安全等级/原因 | `sift-analyze`：本地规则提名 → 可插拔判定器（默认离线规则，可选远程 LLM）→ 路由与护栏 |
| 明确可清理清单本地持久化 | `sift-store`：`cleanable.json` 按路径指纹去重、原子写入、版本化 schema、有上限 |
| 后台监听剩余量并按阈值提示/自动清理 | `sift-monitor`：采样 → 纯函数策略 → 仅清理「Safe 且已批准」的条目，全部进回收站 |

## 2. Crate 分层

依赖方向严格向下（箭头 = 依赖）：

```
        src-tauri (Tauri 适配)        sift-gpui-app (GPUI 适配)
                 │                              │
                 └──────────┬───────────────────┘
                            ▼
                      sift-monitor   （后台监听 + 阈值策略 + 清理执行）
                            │
                      sift-store     （本地持久化：结论/清单/决策/设置）
                            │
                     sift-analyze    （候选提名 + 判定器 + 路由护栏 + 习惯挖掘）
                            │
                       sift-scan     （扫描引擎：调度、预算、事件流）
                            │
                     sift-platform   （系统能力：卷/目录批量读/回收站/监听）
                            │
                       sift-core     （领域模型：arena 树、interner、字节记账、策略）
```

| Crate | 职责 | 明确不做 |
|---|---|---|
| `sift-core` | 领域类型与规则：`ScanTree`、`NameInterner`、`ByteSize`、`NodeKey`、`Volume`、`ScanPolicy`、`Progress`、`ScanEvent`、`Deletable` 策略 | 任何 I/O、任何 UI、任何 toolkit 依赖 |
| `sift-platform` | 系统边界：卷枚举、`getattrlistbulk`/`read_dir` 批量读目录、回收站、文件系统监听、并行目录读取原语 | 不做调度决策、不建树 |
| `sift-scan` | 扫描引擎：优先级队列、协调线程 + 工作线程、预算、事件发布 | 不认识任何前端 |
| `sift-analyze` | 候选规则、安全等级/原因、判定器契约、隐私路由、远程 LLM 适配（feature 门控）、习惯挖掘 | 不落盘、不发网络（远程适配器由调用方注入） |
| `sift-store` | 四份本地文档的读写与去重 | 不知道 UI、不保存密钥 |
| `sift-monitor` | 后台线程 + 纯策略函数 + 可注入的 `Remover` | 不直接调用回收站（走 `Remover`，便于测试与替换） |
| `sift-gpui-app` | 主题、窗口、视图、事件泵 | 布局数学在 `model/treemap.rs`（纯函数、有测试），视图只画 |
| `src-tauri` | Tauri 命令 + 事件协议翻译 | 同上；保留 Svelte 前端原有事件协议不变 |

**为什么不是 `models/` + `views/` + `commands/` 的横向目录？** 因为那样每个能力都被切碎到各处，改动要跨多个目录，删掉一个能力也无法只删一处。按能力分 crate 后，`Cargo.toml` 就是依赖与所有权的可审查声明。

## 3. 扫描引擎

### 3.1 形状：协调者拥有状态，工作线程只做 I/O

```
            优先级队列（协调者独占）
               ▲      │ 派发（上限 = 工作线程数）
               │      ▼
        协调者（建树/发布）   工作线程 × N ── getattrlistbulk ──► 原始条目
               ▲                                    │
               └────────────────────────────────────┘
```

- **协调者线程**独占 `ScanTree` 与所有计数器，从不碰文件系统；
- **工作线程**只读目录、回传原始条目，从不碰树。
- 因此树本身**不需要锁**；外层一把 `Mutex` 只是给 UI 读实时状态用的。
- 并发上限 = 工作线程数：既不会排队过深，也不会空转。

### 3.2 焦点确定性优先

队列是按 `category` 排序的堆：焦点目录(0) → 其祖先(1) → 兄弟(2) → 焦点子树(3) → 其它(4)；非祖先类别按深度浅优先，祖先类别按深度深优先。

仅靠优先级**不够**：焦点与其兄弟会同时被派发给不同工作线程，谁先返回是随机的。因此**在焦点目录被列出之前，协调者只允许 1 个任务在飞**（把并发度压到 1）。这只会让最前面的几次批量读串行——每次都是亚毫秒级——之后立刻恢复满并发，但换来「焦点一定早于任何兄弟/无关子树出现」的确定性。若焦点路径根本不存在（被删除），协调者会在确认无法到达后立刻解除限流。

### 3.3 内存：为什么不存文件节点

- **目录节点 72 字节定长记录**（`key 16 + parent/first_child/next_sibling 12 + name 8 + size 16 + mtime 8 + file_count 4 + flags 1`，对齐后 72）。flags 里打包了 kind + pending + symlink + deletable，避免布尔字段各自占位。
- **文件不建节点**：文件字节直接累加到父目录，然后被遗忘。卷上文件数通常是目录数的 5–10 倍，这是最大的一笔节省。需要文件级明细时（安装包、大文件、重复文件），分析阶段**按需重新枚举少数几个目录**，而不是在扫描时留下百万条记录。
- **名称去重**：所有名字放进一个字节 arena，节点只存 8 字节 `NameRef`；`node_modules`、`target`、`Contents` 这类名字只存一份。
- **硬链接表只收 `nlink > 1` 的文件**：早期实现把每个文件都塞进 `HashMap<FileId,()>`，实测 61 万文件时占用约 24 MB；改为只收多链接文件后降到 0（`/Applications` 没有多链接文件），全盘扫描时 30 万个多链接文件只占 7.4 MB。平台不报告链接数（`nlink == 0`）时不启用去重——**宁可多算，不可少算**。
- **路径不进内存**：路径按需从节点向上重建（O(depth)），所以不存路径。节点的存储路径只在需要发送事件时构造。
- **预算 + 超预算子树「只计大小」**：节点数/深度超限时不再建记录，但该子树仍会被走到并汇总字节（工作线程内迭代完成，不阻塞协调者），因此**总数仍然精确**，内存仍然有界。
- **扫描结束 `shrink_to_fit`**：`Vec` 按倍增扩容，结束后通常闲置 1.5–2 倍容量；一次性拷贝换回长期常驻内存。

### 3.4 实测

`cargo run --release -p sift-scan --example scan_bench -- <path>`，macOS / Apple Silicon / APFS：

| 目标 | 条目 | 耗时 | 速率 | 树常驻内存 | 每节点 |
|---|---|---|---|---|---|
| `/Applications` (57.4 GB) | 610,151 文件 + 78,867 目录 | **2.28 s** | 267,805 文件/s | **7.2 MB** | 95 B（含 interner，已 `shrink_to_fit`） |
| `/` (整卷, 3.8 TB 逻辑) | 13,876,391 文件 + 4,000,000 目录 | **202 s** | 68,611 文件/s | **326 MB**（节点预算打满 4M） | 85.5 B |

（`/Applications` 的常驻内存是加 `shrink_to_fit` 之前测量的 11.1 MB → 之后 7.2 MB：`Vec` 按倍增扩容，扫描结束时通常闲置近一倍容量。）

- 整卷扫描命中 **`GetAttrListBulk` 快路径**（基准会打印实际使用的 reader，避免静默退回可移植路径却看起来像「莫名变慢」）。
- 按整卷速率外推研究给出的目标规模（2 TB ≈ 2M 文件）：**≈ 29 s**，在 60 s 预算内；即使 4M 文件也约 58 s。
- 整卷扫描有 **1,627 个目录被拒绝访问**（TCC 保护，`open` 返回 `EPERM` 而非 `EACCES`），819,273 个目录因节点预算未建记录——两者都被计入 `Progress.denied` / `unrecorded_dirs`，总数仍正确。
- 整卷逻辑字节 3.8 TB 大于卷容量 1.8 TB：这是 macOS **firmlink**（`/` 与 `/System/Volumes/Data` 内容互相可见）造成的重复遍历，属于「逻辑大小」的固有语义，报告中应同时给出物理大小。

> 诚实说明：上表是**热缓存**数据。冷缓存会显著变慢（`getattrlistbulk` 仍需读目录），但研究结论是 Tier 2 批量回退在冷缓存下也能落在 20–35 s/2M 文件，仍在预算内。

### 3.5 平台回退阶梯

| 层 | 机制 | 状态 |
|---|---|---|
| Tier 1 | macOS `getattrlistbulk(2)`（一次调用返回整段目录的元数据）+ `ATTR_FILE_LINKCOUNT` | **已实现并实测**，且与可移植路径逐字段对比通过 |
| Tier 2 | 可移植 `read_dir` + 每条目 `metadata`（线程池并行） | 已实现，作为任何平台/卷的回退 |
| Tier 3 | Windows `FileIdBothDirectoryInfo` / 直读 `$MFT`、Linux `getdents64` + 批量 `statx` | 已调研并写入 `docs/research/fast-disk-scan.md`，未实现 |

macOS 快路径的解析器严格按 `ATTR_CMN_RETURNED_ATTRS` 的**升序位**遍历，而不是固定字段顺序——`man 2 getattrlist` 关于「截断时 length 字段是实际拷贝字节数」的说法在实测中是错的，因此**所有读取都按 `attrBufSize`/chunk 边界做上界检查**，解析失败一律回退可移植路径而不是继续读。

## 4. 智能分析

### 4.1 三段式，顺序不可颠倒

1. **本地规则提名候选**（`rules.rs`）：可重建缓存、应用缓存、日志、回收站、安装包/压缩包、长期未动的大文件、同目录同名同大小重复。规则是确定、可审计、免费的；**它也决定了什么有资格被送出本机**。
2. **判定器给出安全等级/原因**（`adjudicate.rs`）：离线规则判定器默认使用；远程 LLM 只能**确认或削弱**，不能凭空产生 `Safe`。
3. **路由决定什么可以离开本机**（`route.rs`）：结构性家族（缓存、构建产物、回收站）本地判定、**永不上传**；只有「安全性取决于内容是什么」的家族（陈旧大文件、压缩包、安装包、重复组）才会被发送，且只发送**脱敏路径**。

安全等级只有三档，且**缺省是 `Review`**：任何缺失、畸形、被拒绝的判定都落到 `Review`，它可见但**永不**可自动清理。`Safe` 是唯一可自动清理的档位。

### 4.2 单一口径：结论来自提名它的规则

候选自身携带 `Nomination { rule, safety, reason_key, reason_param, detail_key }`，判定器只是**忠实复述**它，而不是按规则名再查一张表推导一遍。

这个设计是被实测逼出来的：早期版本在判定器里维护「规则 id → 安全等级」的映射表，于是规则里加的细化判断会被静默丢弃——`/Applications` 里 `ChatGPT.app/Contents/Resources/…/node_modules` 明明是安装包内部目录（用户没有工具链重建，删掉只会让应用坏掉），规则已经把它降级为 `Review`，判定器却又按 `dir.node_modules` 把它改回 `Safe`。真机上跑一次才发现：它会建议用户删掉已安装应用内部的文件。

现在：**应用包内部的「可重建」目录一律 `Review`**，理由用独立的 i18n key（`reason.insideBundle`）说明原因；项目目录里的同名目录仍然是 `Safe`。没有 `Nomination` 的候选一律 `Review`——可见，但永不可自动删除。

### 4.3 模型不能单独授权删除

`sanitize_model_verdict` 是远程答案进入系统的唯一入口，规则是：

- 模型可以**更保守**（`Keep` / `Review` 直接通过）；
- 模型说 `Safe` 时，必须同时满足：该家族允许模型授权、策略未全局关闭、且置信度 ≥ 远程阈值（默认 0.85）——否则降级为 `Review` 并保留模型的解释，同时用 i18n key 明确说明「已被降级」；
- 编造的 id 被丢弃；漏答的条目变成 `Review`；批量失败也变成 `Review`（网络问题只会让分析**退化**，不会让它越权）。

### 4.4 隐私边界

- 只发送：脱敏路径（`~/Downloads/x.dmg`）、是否目录、大小、天数、家族、命中的规则信号；
- **从不发送**：真实绝对路径、文件内容、其它候选；
- 远程能力编译期由 `remote-ai` feature 门控、运行期需要**显式同意**（`AiSettings::consent_granted`）；
- **API Key 不落盘**：设置里只存环境变量名（`apiKeyEnv`），有测试断言序列化后的设置里不出现密钥字段。

### 4.5 结论持久化与习惯挖掘

- 判定结果按 `PathFingerprint { 路径 key, 大小, mtime, 是否目录 }` 去重缓存；指纹任一分量变化即失效，避免「4 GB 缓存的结论」被套用到后来占位的别的东西上。
- `cleanable.json` 只存 `Safe` 条目（**Review 是问题，不是长期许可**）；重新分析若降级，条目会被移出并报告。
- 每个条目的「允许自动清理」是**逐条**的、且**跨重新确认保留**；但如果对象变了（指纹不匹配）则自动撤销——许可是针对那个对象给的。
- 决策日志按「名字 + 家族」聚合；只有**跨 ≥3 个不同日期**重复出现才会建议为例行任务，一次清理会话无法凭空造出习惯；重复「保留」会反向抑制提示。

## 5. 后台监控与自动清理

策略是一个**纯函数** `evaluate(config, sample, entries, home, last_clean, last_notify, now)`，所有「是否可以不经询问就删」的规则都在这一屏里读完并被穷举测试：

1. 只有 `Safe` **且**已逐条批准的条目会被选中；
2. `home_only` 时主目录之外的条目一律不选（无法证明在主目录内 → 拒绝）；
3. 超过 `max_auto_clean_bytes` 的批次**绝不拆分、绝不截断**，而是转为「需要确认」；
4. 冷却期内不重复清理；通知也有独立冷却（抑制重复通知但**不隐藏等级**）；
5. `Off` / `NotifyOnly` 永不选中任何条目——紧急程度**不会**放宽规则。

执行前还会对每个条目**重新校验指纹**（目录按 mtime + 类型，文件按大小 + mtime），然后才调用可注入的 `Remover`；生产实现是系统回收站，失败按条目回报且失败的条目**留在清单里**。这条「删除前再验证一次」的规则是被集成测试逼出来的：目录记住的「大小」是**子树汇总**而不是 `st_size`（APFS 上是 0），所以对目录只能比较 mtime 与类型，这一点在代码与测试里都写明了。

## 6. 两个前端共享同一份核心

- Tauri 侧：`scanner.rs`/`disks.rs`/`cleanup.rs`/`watcher.rs`/`analyze.rs` 全是适配层。「目录已列出」批事件被翻译回 Svelte 前端原有的 `scan://discovered` / `scan://sized` / `scan://progress` / `scan://done` 协议，因此**原有界面无需改动**（`pnpm check` 0 错误、`pnpm build` 通过）。
- GPUI 侧：视图层只渲染 `WorkspaceModel`（纯数据、无 GPUI 依赖、有单元测试），布局数学在 `model/treemap.rs`（纯函数、有单元测试）。
- 两侧共用同一套事件、同一套判定器、同一份持久化格式，所以同一个结论在两个界面里的数字与理由必然一致。

## 7. 测试策略

| 层 | 覆盖 |
|---|---|
| 纯逻辑 | 名称 interner 冲突链、arena 树聚合/幂等关闭、treemap 布局（不重叠/不溢出/单调）、习惯挖掘阈值、策略函数全分支、护栏降级 |
| 平台 | macOS 快路径与可移植路径**逐字段对比**（真实目录树）；硬链接链接数；卷枚举；`free_space` 前缀解析 |
| 引擎 | 真实临时树端到端：尺寸汇总、焦点确定性优先、取消、预算拒绝后仍精确计数 |
| 持久化 | 原子写、损坏文件归档、schema 版本不符归档、容量上限、指纹失效 |
| 集成 | 扫描→分析→落盘→重启保留→阈值策略→清理→失败回报→习惯挖掘（4 个不同日期）|
| 前端 | Tauri 适配 DTO/事件形状；GPUI 模型事件应用、导航、选择、裁剪、treemap 折叠 |

需要系统权限的用例（真实回收站、FSEvents）标记 `#[ignore]` 并写明原因，默认不阻塞 CI，但在真实会话中可运行。

## 8. 当前状态与后续

已实现并验证（`cargo test --workspace` 278 项通过、`cargo clippy --workspace --all-targets` 干净、`pnpm check` 0 错误）：

- 六个核心 crate + Tauri 适配层（Svelte 前端事件协议未变）+ GPUI 原生前端（能启动并渲染窗口）。
- macOS `getattrlistbulk` 快路径与可移植路径逐字段一致性测试；硬链接链接数读取。
- 分析闭环：规则提名 → 判定 → 落盘 → 阈值策略 → 清理 → 习惯挖掘，且有端到端集成测试。

GPUI 视图层覆盖了原设计的全部表面：

| 表面 | 实现 |
|---|---|
| 标题栏 | 应用标识 + 实时状态 + 值守开关 + 扫描（进行中为禁用态）+ 面板切换 |

### 8.1 UI 交互级测试

### 8.2 设计稿还原（§9 之前的这一轮返工）

第一版 GPUI 界面是**照设计稿意译**的，不是照抄：布局近似、颜色手挑、尺寸取整。反馈是「还原度极差」，根因有三条，都不是审美问题而是**具体的实现错误**：

1. **颜色构造用错了函数**。`gpui::rgba(hex)` 接收的是 **8 位 RGBA**（`[r,g,b,a] = hex.to_be_bytes()`），传 6 位设计令牌 `0x07090C` 会被读成 `[0x00,0x07,0x09,0x0C]`——**几乎全透明**。整份调色板都该用 `rgb()`。这一条会让所有表面发灰发透。
2. **treemap 坐标重复叠加原点**。`squarify` 返回的矩形已经是传入 area 的坐标系（我把绝对窗口坐标传进去了），渲染时又加了一次 `bounds.origin`，整张图被平移（偏移量正好等于舞台原点）。
3. **标签 run 长度写死为 1 字节**。`text_style().to_run(1)` 只塑造一个字节，于是每个方块的名字都只画出首字母（`Library` → `L`）。

修完之后，还原**不再靠肉眼**，而是三条可复现的证据链：

**(a) 颜色：像素级对齐。** 渲染真实视图到 PNG，再直接读像素（`tools/png_sample.py`，纯标准库解码 PNG）：

| 元素 | 设计稿令牌 | 期望合成 | 实测像素 | |
|---|---|---|---|---|
| 窗口底 | `oklch(0.138 0.009 255)` | `#07090C` | `#07090C` | 精确 |
| 画布 | `surface` 52% over bg | `#0B0E12` | `#0B0E12` | 精确 |
| 玻璃导航 | `surface` 86% over bg | `#0E1115` | `#0E1115` | 精确 |
| 列表栏 | `bg` 30% over canvas | `#0A0C10` | `#0A0D0F` | ±1（内阴影） |
| 方块填充 | `cat-1` @0.92 | `#2C87D1` | `#2C86D1` | ±1（渐变插值） |

**(b) 尺寸：在测试里量出来。** `the_shell_frames_match_the_design` 渲染后取两个相邻行按钮的 y 差，断言行距 = `metrics::ROW_H` = **32px**（18px 图标槽 + 上下 7px）；`theme::tests` 断言 46 / 268 / 1180 / 20 / 28 / 14 / 1.5 等帧值。截图能看出「高度不对」，只有数字能阻止它漂回去。

**(c) 每个设计令牌一个 owner。** 调色板（oklch→sRGB 精确换算）、字号（13.5/12.5/11/10.5…）、字重（480/550/560/600/650，`FontWeight(pub f32)` 可以给任意值，不必四舍五入到 `SEMIBOLD`）、帧尺寸、阴影配方、渐变系数（0.92→0.62、压暗 0.34、hover 提亮 1.12）全部集中在 `crates/sift-gpui-app/src/theme.rs`；视图里不留字面量，所以「像不像设计稿」只有一个地方需要审。

**怎么看界面。** GPUI 的 `Window::render_to_image` 走 headless Metal，不需要录屏权限：

```sh
cargo test -p sift-gpui-app --test rendering   # 写 crates/sift-gpui-app/target/ui-shots/{shell,popup,scanning}.png
python3 tools/png_sample.py <png> X Y ...      # 读任意像素/区域均值
```

`tests/rendering.rs` 用一份「开发者主目录」的真实规模清单（38GB 的 Library、12GB 的 Docker.raw、长尾）渲染三种状态，因此布局的极端情况（超长名、长尾折叠、空态、扫描中）都在图上可查。

**这一轮从截图上抓到的缺陷**：方块标签只显示首字母、整图平移、行高 27px（应 32px）、`Photos Library.photoslibrary` 把大小列挤出面板（缺 `truncate`）、列表不能滚动、候选弹层高度随内容塌缩（设计稿是固定高）、页脚主按钮没靠右、文件行多了一个设计稿没有的高亮底色（设计稿只用 `row-dim` 压暗其余项）。

### 8.3 三个逻辑错误的根因（第二轮返工）

截图对得上了，但用起来还是错的。三条反馈都追到了具体代码：

**1. 「磁盘目录的数据错误，逻辑关系异常」——选中的磁盘没有写进模型。**

`accept_volumes` 把选中的卷存进 `Services` 自己的字段，然后直接开始扫描，**从未调用 `model.select_volume(..)`**。于是模型里 `current_volume` 是 `None`：选择器只能显示「—」，底部胶囊拿不到可用空间——而同一时刻正在扫这块盘。这是"两个地方各存一份真相"的典型后果。

修法不是补一次调用，而是把选择策略搬到状态所在的模型里：新增 `WorkspaceModel::adopt_volumes(volumes) -> Option<Volume>`，由它决定「保留当前盘还是选系统盘」，并保证「同一份列表刷新时不丢掉正在看的树」。Services 只剩remember 答案。

回归测试 `the_window_knows_its_disk_and_waits_to_be_asked` 走**真实卷枚举**（`sift_platform::volume::list_volumes()` → `Services::refresh_volumes` → 模型），断言模型知道盘名且没有开扫。`refresh_volumes` 不是测试专用口子：UI 的磁盘刷新本来就需要一个同步重列入口（启动路径那条走后台线程 + 泵）。

**2. 「文件夹的样式错误，与 tauri 差距巨大」——图标不是同一套。**

设计稿**没有用图标库**：`src/lib/components/Icon.svelte` 里是一张手写的 24×24 路径表，`fill="none" stroke="currentColor" stroke-width="1.7"` 圆角端点。我这边用的是 GPUI Kit 的 Lucide 目录（线宽 2、几何不同）。文件夹的折角、硬盘的圆角矩形因此明显不是一个东西。

现在 `assets/sift-icons/*.svg` 逐条誊写设计稿的 `d` 属性（folder / hard-drive / external-drive / check / x / chevron-* / refresh / spark / layers / search / trash / alert / info / home / lock / clock / bolt / file，共 20 个），由 `assets::SiftAssets` 以 `sift-icons/<name>.svg` 提供，`stroke="currentColor"` 让颜色跟随主题令牌；非本命名空间的路径回落到 GPUI Kit 自己的目录，组件图标照常。`gpui-kit-assets` 依赖随之删除。

**3. 「不是启动就开始检索，需要点击触发开关才开始」——启动不再自动扫描。**

设计稿的 `store.init()` 其实是 `listVolumes()` → `selectVolume()` → `startScan()`，即**启动即扫**；按你的要求改成显式触发，这是**有意偏离设计稿**，已在 §8.3 表里记明：

- 启动只做「列盘 + 选盘」，不扫；
- 唯一开扫入口是标题栏的「智能扫描」按钮（`Services::restart_scan`）；
- 从选择器换盘也只切表面、不开扫——换盘看一眼不该付出几分钟的扫描代价；
- 模型新增 `has_started()`，让界面能区分「还没扫」与「扫过但是没有内容」。此前未扫描的空窗口会显示「此文件夹没有可显示的内容」——那是一句对磁盘的错误陈述；现在是「点击「智能扫描」开始」/「尚未扫描」。
